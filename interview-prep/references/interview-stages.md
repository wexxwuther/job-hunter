# Interview stages, STAR stories, and gap bridges

How to prep for each stage `build_prep_pack.py` supports. The question banks live in
the script (`STAGES`); this file is the strategy behind them. Written for every kind
of job: nurses, welders, teachers, analysts, engineers.

## Stages

### recruiter_screen

Recruiter or HR, 15-30 minutes, often by phone. Tests motivation, basic fit, and
logistics. Answers should be short: a 60-second "tell me about yourself", one line on
why this role, a clear answer on pay expectations (a range the user chose, never a
number the agent picked), start date, location or schedule. Save full stories for
later rounds.

### hiring_manager

The person the user would report to. Tests "can you do this job and would I want to
manage you". Expect the posting's requirements one by one and 2-3 full STAR stories.
The requirement map in the pack is the core of this stage.

### skills

A practical test: coding or tools exercise, clinical or safety scenario, trade test,
teaching demo, writing sample, data task. Prep is about reasoning out loud: state the
goal, what you would check first, the steps, how you would confirm it is right or
safe, and what you would ask. The user should only claim tools and methods they have
actually used.

### behavioral_panel

Several interviewers asking "tell me about a time" questions, usually scored on a
rubric. Every answer is a STAR story of about two minutes, focused on what the user
personally did. Have 5-6 distinct stories so the same one is not reused for every
question.

### case_presentation

A problem to solve live, or a presentation prepared in advance. They watch structure,
assumptions, use of evidence, and how pushback is handled. Prep: a simple structure
(goal, options, recommendation, risks), saying assumptions out loud, and a plan for
"what data would you want".

### final

Senior leaders or a culture round. Fewer details, more judgment and motivation: why
this organization now, where the user wants to go, the hardest decision they made,
anything that would stop them accepting. Tie the user's real story to where the
organization says it is going (from verified research only).

## STAR stories

- **Situation:** where and when (job, school, volunteer role, project).
- **Task:** what the user was responsible for.
- **Action:** what the user did, in "I" statements, 2-4 concrete steps.
- **Result:** what happened. Numbers only if the user can stand behind them in a
  follow-up question. "The weekly report went out on time every week" beats an
  invented percentage.

The pack seeds each story with a real line from the submitted resume or cover letter
(the "starting point"). The match is keyword overlap, so it is a suggestion: the user
confirms it really answers the question. If no real example fits, say so and ask; do
not stretch a line to cover a requirement it does not meet (a date range is not "5+
years" unless it adds up).

## Gap bridges

For a requirement nothing the user sent covers:

1. Ask first: have they done it anywhere, paid or not? If yes, it becomes a STAR story
   and the fact goes into `facts.txt`.
2. If no, use the bridge: acknowledge it plainly, name the closest real experience,
   say how they would get up to speed. Never imply experience the user does not have,
   and never coach the user to dodge or blur the question.

## Questions to ask

Pick at least two. Good questions show the user read the posting and want to do the
job well: success in the first 90 days, the hardest part of the job, how the team
works, what the next steps are. Questions built on company research must use only
verified facts.

## Lessons

`.job-hunter/LESSONS.md` entries are patterns the user confirmed. Quote them as
written; use them to shape emphasis (for example "lead with the result"). A lesson is
never a fact about the user's experience.
